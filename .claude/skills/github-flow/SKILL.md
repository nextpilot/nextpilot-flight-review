# GitHub Flow 开发流程

main 是唯一长期分支、始终可发布可回退。所有改动经短命特性分支进入 main，不设 develop 等中间分支。

## 1. 流程总览

```
main（可发布）
   │ 1. 切分支        2. 提交推送        3. 建 PR        4. 验证+评审       5. 合并删分支
   ├──> feat/xxx ──────────> origin ──────> PR ────────> CI/ctest 绿 + 评审 ──> 合入 main，删除特性分支
```

## 2. 分支规则

| 规则 | 内容 |
|---|---|
| 命名 | `<类型>/<简述>`：`feat/`、`fix/`、`docs/`、`refactor/`、`chore/`（如 `feat/toolbox-installer`） |
| 寿命 | 短命：一个分支只承载一个工作单元（对应一个 issue），完成后即删 |
| 起点 | 一律从最新 main 切出；开工前先 `git pull` |
| 禁止 | 直接向 main push（用户显式授权的例外除外）；复用已合并分支；一个分支夹带多个不相关改动 |

## 3. 提交纪律

- 一个提交一个完整语义单元（编译通过、不破坏测试）；禁止"临时存一版"的废提交。
- 提交信息：`<type>: <动宾短语>`（type 同分支类型前缀），正文写清楚做了什么、为什么。写给人看，不写口号。
- 提交信息里引用 issue 编号（gitee 网页链接的尾段，如 `IKX5DP`），便于自动关联。

## 4. PR 规则

1. 推送特性分支后在 gitee 建 PR：`base: main ← compare: feat/xxx`。
2. PR 描述必含：做什么、关联 issue、验证方式与结果（测试数字）。
3. 合并门槛（全部满足才能合）：
   - 全量编译无 error；
   - ctest 全绿（回归口径见 `docs/develop/testing.md`）；
   - 无越层依赖（分层守卫随 configure 强制）；
   - 涉及架构/契约/文档的改动已同步对应文档。
4. 合并方式：普通 merge 或 squash（保持 main 历史线性、每节点语义完整）。
5. 合并后**立即删除特性分支**（本地+远端）。

## 5. AI 执行者的附加纪律

- AI 不直接 push main；即使是文档小改也走特性分支 + PR。
- 用户显式说「直接推 main / 强推」时可例外执行，其余一律走 PR。
- 若 PR 验证失败：修复后追加提交再推，不 amend 已推送的提交。
- 迁移期间例外：当前处于仓库重构迁移期，结构性大改（目录重组、历史清理）经用户拍板可单节点强推 main；迁移定稿后本例外作废，一律 GitHub Flow。

## 6. 与 task-plan 的衔接

- 特性分支对应一个 issue（见 task-plan skill）；PR 描述引用该 issue。
- 完成判定遵循 task-plan：验收全绿 + 回填评论 + 推送 + issue 关闭。
