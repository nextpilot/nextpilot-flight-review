# Git 提交与推送强制规范

## 一、目的与适用范围

本规范约束 AI 在执行 `git commit` 与 `git push` 时的分支纪律，防止未经验证的提交进入主干分支。适用于一切代码提交与推送操作，无例外条款。

规范区分三个阶段：**开发期**（编码与本地验证）不受分支限制；**提交期**（git commit）与**推送期**（git push）受下列规则约束。

## 二、核心规则

| 阶段 | 规则 |
|---|---|
| 开发期 | 允许在当前分支（含主干）上编码、运行测试，工作过程不受分支限制 |
| 提交期 | 禁止将 feature 提交直接落在主干分支（`main` `master` `develop` `dev` `trunk` 及 `release*`）并推送；检测到当前处于主干分支时，应先检出特性分支再提交 |
| 推送期 | 特性分支完成提交且测试通过后，应 `git fetch` 并 `rebase` 至原分支（目标主干）最新，再推送特性分支；禁止直接推送主干分支，除非用户明确指令且该分支确属允许范围 |

## 三、执行流程

### 步骤 1：判定当前分支

```bash
git branch --show-current
```

- 当前为特性分支（任意非主干名称）→ 转步骤 3。
- 当前为主干分支（命中第二节保护清单）→ 转步骤 2。
- HEAD 游离或仓库无提交 → 应先与用户确认后再操作。

### 步骤 2：从主干检出特性分支

当前处于主干分支且存在或将产生 feature 改动时：

```bash
git checkout -b feature/<简短英文标识>
```

- 未提交改动随分支检出自动携带，无需 stash。
- 分支命名：功能用 `feature/<做什么>`，缺陷修复用 `fix/<问题>`；项目已有命名惯例优先。
- 主干上已有的未推送本地 feature 提交随分支一并携带，检出后主干回退至远端原点。
- 禁止在主干分支上先执行 `git commit` 再行迁移；应先检出特性分支，后提交。

### 步骤 3：提交与测试（在特性分支上）

1. `git add` 相关文件后提交；提交信息应说明改动内容与原因，禁止使用 `update`、`fix` 等无信息量的表述。
2. 推送前测试必须通过：运行项目测试（ctest/pytest/npm test 等），失败则先修复再推送；无测试条件时应在提交说明中注明。
3. 相互独立的改动应拆分为多个提交，禁止合并为单一提交。

### 步骤 4：rebase 后推送

```bash
git fetch origin
git rebase origin/<原分支>
git push origin <特性分支>
```

- rebase 冲突应逐个解决后 `git rebase --continue`；无法解决时执行 `git rebase --abort` 回滚并报告用户。禁止为绕过冲突改用 merge 提交或强制推送。
- 推送被拒（远端存在新提交）时，重新执行本步骤；禁止使用 `--force`。
- `--force` 与 `--no-verify` 仅在用户明确要求时使用；hook 失败表明存在真实问题，应修复根因。
- 用户明确要求推送至原分支且该分支属其个人长期分支、流程允许时：先 fetch + rebase 确认线性后执行 `git push origin HEAD:<原分支>`，测试仍须通过。此例外不适用于 main/master/develop 等主干保护分支。

## 四、推送前自检清单

推送前逐项确认，任一项不满足则中止推送并回到对应步骤：

- [ ] 待推送 ref 不是 main/master/develop 等主干分支。
- [ ] 全部提交落在特性分支（`git log origin/<主干>..HEAD` 仅包含本次 feature 提交）。
- [ ] 测试已运行且全部通过。
- [ ] 已 rebase 至远端最新，未基于过期状态推送。
