# 任务计划（Plan）编写规范

## 1. 目的与适用范围

Plan 是设计师与执行 agent 之间的**完整工作契约**：执行 agent 不依赖对话历史、口头说明或其他隐含上下文，仅凭 plan 即可正确开工并交付。本规范适用于所有以"设计→派发→执行→验收"方式推进的开发任务。

Plan 不承担的职责：系统性方案设计（归里程碑设计文档）、长期路线规划（归 roadmap 总表）。Plan 只承载**单个可独立验收的工作单元**。

## 2. 角色与职责

| 角色 | 职责 | 禁止事项 |
|---|---|---|
| 设计师 | 定稿方案、编写 plan、验收交付 | 方案未定稿不得派发 plan；口头派发无效 |
| 执行 agent | 依照 plan 实施、验证、回填完成情况 | 发现 plan 缺陷时不得自行变更方案，应中止并报告 |
| 用户 | 验收与批准 | —— |

## 3. Plan 载体管理（issue）

Plan 一律以 **gitee issue 为唯一载体**，禁止在仓库写 plan md 文件（避免污染仓库；历史 plan 文件已全部转 issue 并删除）。

- **平台**：gitee（仓库 `nextpilot/nextpilot-advance-plotscope`）；后续迁移 GitHub 时随仓库一起搬。
- **组织**：一个大阶段（里程碑）建一个**父 issue**（总 Plan，任务清单串联子项）+ 里程碑（Milestone，同名）；每个工作单元一个**子 issue**，独立派发、评论、关闭。大 plan 可在子 issue 内继续分节，不拆更细。
- **标题命名**：`[<阶段字母><步骤号><子步骤字母>] <动宾标题>`（如 `[P1a] 机制库 libs/archive：ZipReader zip 读端`）。编号为三级结构：
  - **阶段字母**：标识所属大阶段，由设计师自选（如主题首字母或 `P`，同一主题内应一致）；
  - **步骤号**：主题内执行顺序，与所属里程碑条目号对应（M3.1 → `1`，M3.2 → `2`）；
  - **子步骤字母**（可选）：同一步骤内的细分（`a`、`b`…），如 M3.1a → `P1a`。
- **标签**：主题标签（如 `M3`、`toolbox`）+ 归属里程碑。
- **粒度**：一个 issue 对应一个可独立验收的工作单元；禁止将多个工作单元合并入同一 issue。
- **状态**：issue 开关即状态（open = 待执行/进行中，评论回填后关闭 = 完成）。完成后在本 issue 评论回填「完成情况」再关闭，issue 永久可查。
- **正文清理义务**：issue 正文引用设计文档用仓库相对路径锚点；引用已删除文件的回填条目必须在转 issue 时清理。

## 4. Plan 必备内容

一份完整的 plan 依次回答六个问题，各章节与其对应；章节序号与标题按下表执行，不得增删合并。

| 问题 | 章节 | 说明 |
|---|---|---|
| 为什么做 | ① 任务标识 ② 背景与依据 | 问题陈述、现状、依赖 |
| 做什么 | ③ 目标与范围 | 含明确排除项 |
| 怎么做 | ④ 设计方案 | 决策、接口、格式 |
| 在哪做 | ⑤ 变更清单 | 文件级、含禁区 |
| 怎么做对 | ⑥ 实施步骤 ⑦ 验收标准 | 步步可验证 |
| 怎么算做完 | ⑧ 完成记录 ⑨ 交付后义务 | 回填与同步 |

### ① 任务标识

阶段编号、动宾结构标题、状态行（状态/执行 agent/验收人/关联里程碑条目号）。

### ② 背景与依据

必须包含三类要素，缺一视为 plan 不合格：
1. **问题陈述**：现状缺陷或需求来源，说明为何需要本单元；
2. **现状盘点**：已有底座（给出代码路径）与缺口；可复用的既有机制须明确指出，禁止重复造轮子；
3. **依赖声明**：前置工作单元（给 issue 链接）、引用的设计文档**章节锚点**（如 `docs/roadmap/M3-工具箱生态.md §5`）。

### ③ 目标与范围

- 目标以**可观测结果**表述（接口可用、测试通过、场景跑通），不使用"完善""优化"等不可验收动词单独成条；
- **排除项必须显式列出**：本单元明确不做的内容，防止执行范围蔓延。

### ④ 设计方案

- 仅记录**本单元新产生的设计决策**：接口草图（函数签名/数据格式/意图命名）、关键决策及其理由；
- 与里程碑设计文档重复的内容以锚点引用，禁止复制粘贴全文（双份文本必然漂移）；
- 设计文档未覆盖、本单元需要临时决定的细节，在此处补充并标注"本单元拍板"。

### ⑤ 变更清单

三类列表，**精确到文件路径**，不得使用"相关模块"等模糊表述：
- 新增：路径 + 一句说明（含构建系统接线）；
- 修改：路径 + 预期变更内容；
- 禁止触碰：路径 + 原因（他人占用 / 存量老树 / 命名与分层红线）。

### ⑥ 实施步骤

- 按施工顺序编号，**每一步附带验证方式**（编译通过 / 单测项 / 手动操作与预期现象）；
- 末步固定为全量回归，回归口径写明（构建配置 × 测试命令 × 通过标准）。

### ⑦ 验收标准

- 逐条可判定：测试名、行为断言、量化指标（性能数字/时长）、产物（截图路径）；
- 回归口径为固定条目；
- 禁止"基本可用""大致正常"等不可判定表述——任何一条无法机械判定，即不合格。

### ⑧ 完成记录

由执行 agent **完成后回填**，禁止预填。仅记录事实：提交号、实际变更文件（与⑤对照，超出须说明原因）、测试结果（数字）、与 plan 的偏差（做了什么 plan 未写的、什么未做、原因）。禁止"基本完成"一类不可判定结论。

### ⑨ 交付后义务

完成即必须同步的文档与代码清单：roadmap 状态行、里程碑文档实施结果节、受影响的契约/术语/架构文档。**验收标准全绿但本节未执行，任务不视为完成。**

## 5. 质量标准（验收一份 plan 的尺子）

1. **自包含**：不读对话历史即可开工；
2. **可判定**：验收标准每条可机械判定，步骤每步有验证方式；
3. **单一事实来源**：设计内容只在设计文档或 plan 一处完整存在，另一处用锚点引用；
4. **边界明确**：范围排除项、禁止触碰清单完备；
5. **最小必要**：不包含与本单元无关的内容，发现超范围需求记入后续 plan 而非本 plan。

## 6. 流程纪律

1. 派发：设计师建 issue（含完整 plan 内容）→ 用户同意 → 指派执行 agent。issue 是唯一派发物。
2. 执行：执行 agent 按序实施；遇 plan 缺陷（错误/缺失/依赖不满足）立即中止并报告，不得自行变更方案、降低验收标准或扩大范围。
3. 回填：完成后在本 issue 评论填写⑧、执行⑨，然后提交推送。
4. 验收：用户按⑦逐条验收；通过后关闭 issue。
5. 完成 = ⑦全部通过 ∧ ⑨已执行 ∧ 已推送 ∧ issue 已关闭，四者缺一不视为完成。

## 7. 标准模板

```markdown
# [<阶段字母><步骤号><子步骤字母>] <动宾标题>

> 状态：待执行｜执行 agent：（领取后填写）｜验收人：（用户）
> 关联：里程碑条目 <M3.x>｜设计依据 <设计文档 §锚点>

## ① 任务标识
<编号、标题、状态行；一句话任务陈述>

## ② 背景与依据
- 问题陈述：<为何需要本单元>
- 现状盘点：<已有底座（代码路径）/ 缺口>
- 依赖：<前置 plan 链接 / 设计文档锚点>

## ③ 目标与范围
- 目标：<可观测结果>
- 排除项：<本单元明确不做>

## ④ 设计方案
<本单元新增决策：接口草图 / 数据格式 / 理由；重复内容给锚点>

## ⑤ 变更清单
- 新增：`path`（说明）
- 修改：`path`（变更内容）
- 禁止触碰：`path`（原因）

## ⑥ 实施步骤
1. <步骤>（验证：<判定方式>）
2. …
N. 全量回归（口径：<配置 × 命令 × 通过标准>）

## ⑦ 验收标准
- [ ] <测试名 / 行为断言 / 量化指标 / 产物>
- [ ] 回归：<口径>

## ⑧ 完成记录
（执行 agent 回填：提交号 / 实际变更 / 测试结果 / 偏差）

## ⑨ 交付后义务
- [ ] <文档/代码同步项>
```
