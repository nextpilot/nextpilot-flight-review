# issue 编写规范

Plan 是 PM 与 Dev 之间的**完整工作契约**：Dev 不依赖对话历史，仅凭 issue 正文即可正确开工并交付。

## 载体与组织

- **唯一载体**：Gitee issue；禁止在仓库写 plan md 文件，避免污染仓库。
- **平台**：`nextpilot/nextpilot-advance-plotscope`；后续迁 GitHub 随仓库一起搬。
- **组织**：大阶段建一个**父 issue**（总 Plan + 任务清单）+ 同名里程碑；每个工作单元一个**子 issue**，独立派发、评论、关闭。
- **标题**：`[<阶段字母><步骤号><子步骤字母>] <动宾标题>`，如 `[P1a] 机制库 libs/archive：ZipReader 读端`。阶段字母自选但同主题一致；步骤号对应里程碑条目；子步骤字母可选。
- **标签**：主题标签（如 `M3`、`toolbox`）+ 归属里程碑；有状态标签时再加 `status/*`。
- **粒度**：一个 issue = 一个可独立验收的工作单元，禁止多个工作单元合并。
- **归属**：issue 由 PM 创建和维护，Dev 领取后负责实现和进度回填。
- **状态**：Gitee 的 open/closed 是平台状态；工作状态 `ready / in-progress / in-review / blocked / closed` 写在 issue 正文顶部或最新评论。

## 内容构成（6 问 → 9 章节）

| 问题 | 章节 | 要点 |
|---|---|---|
| 为什么做 | ① 任务标识 ② 背景与依据 | ①编号/动宾标题/状态行（状态/负责人/验收人/里程碑条目）；②问题陈述、现状盘点（给代码路径、可复用机制禁止重造）、依赖声明（前置 issue 链接 + 设计文档章节锚点） |
| 做什么 | ③ 目标与范围 | 目标用**可观测结果**表述，不用“完善/优化”单独成条；**排除项必须显式列出** |
| 怎么做 | ④ 设计方案 | 只记本单元新决策（接口草图/数据格式/理由）；与里程碑文档重复处用锚点引用，禁止复制全文；临时决定标注“本单元拍板” |
| 在哪做 | ⑤ 变更清单 | 精确到文件路径：新增/修改/禁止触碰（后者给原因），禁用“相关模块”等模糊表述 |
| 怎么做对 | ⑥ 实施步骤 ⑦ 验收标准 | ⑥按施工顺序编号、每步附验证方式、末步固定全量回归（写清配置×命令×通过标准）；⑦逐条可判定（测试名/行为断言/量化指标/产物），禁止“基本可用”等表述 |
| 怎么算做完 | ⑧ 完成记录 ⑨ 交付后义务 | ⑧由 Dev **完成后回填**、禁止预填，只记事实；⑨完成即须同步的文档/代码清单，未执行不算完成 |

## 质量标准

1. **自包含**：不读对话历史即可开工。
2. **可判定**：验收标准每条可机械判定，步骤每步有验证方式。
3. **单一事实来源**：设计内容只在设计文档或 plan 一处完整存在，另一处用锚点引用。
4. **边界明确**：排除项与禁止触碰清单完备。
5. **最小必要**：不含无关内容，超范围需求记入后续 issue。

## 标准模板

```markdown
# [<阶段字母><步骤号><子步骤字母>] <动宾标题>

> 状态：ready｜负责人：PM/Dev（领取后填写）｜验收人：PM/用户
> 关联：里程碑条目 <Mx.y>｜设计依据 <设计文档 §锚点>

## ① 任务标识
<编号、标题、状态行；一句话任务陈述>

## ② 背景与依据
- 问题陈述：<为何需要本单元>
- 现状盘点：<已有底座（代码路径）/ 缺口>
- 依赖：<前置 issue 链接 / 设计文档锚点>

## ③ 目标与范围
- 目标：<可观测结果>
- 排除项：<本单元明确不做>

## ④ 设计方案
<本单元新增决策：接口草图 / 数据格式 / 理由；重复内容给锚点>

## ⑤ 变更清单
- 新增：`path`（说明）
- 修改：`path`（变更内容）
- 禁止触碰：`path`（原因）

## ⑥ 实施步骤
1. <步骤>（验证：<判定方式>）
N. 全量回归（口径：<配置 × 命令 × 通过标准>）

## ⑦ 验收标准
- [ ] <测试名 / 行为断言 / 量化指标 / 产物>
- [ ] 回归：<口径>

## ⑧ 完成记录
（Dev 回填：提交号 / 实际变更 / 测试结果 / 偏差）

## ⑨ 交付后义务
- [ ] <文档/代码同步项>
```
