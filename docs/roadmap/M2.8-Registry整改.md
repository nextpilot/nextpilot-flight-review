## 1. 背景与诊断

### 1.1 现状：九张注册表，三种写法，没有共同根基

| 注册表 | 位置 | 形态 | API 方言 | 信号 |
|---|---|---|---|---|
| `Registry<T,Key>`（模板） | libs/registry/include/Registry.h | 纯类型有序容器 | insert/find/value/keys | 无 |
| `StaticRegistry/AutoRegistrar` | libs/registry/include/StaticAutoRegistry.h | 静态自注册 | insert | 无 |
| `DatasetRegistry` | libs/dataset/include/DatasetRegistry.h | QObject 壳+委托模板 | add/get/remove/**ids** | datasetAdded/Removed(id) |
| `SourceRegistry` | libs/dataset/include/SourceRegistry.h | 独立手写容器 | 又一套 | 有 |
| `DerivedSeriesRegistry` | libs/context/include/DerivedSeriesRegistry.h | QObject 独立容器 | 又一套 | derivedSeriesReady |
| `InteractionRegistry` | libs/context/include/InteractionRegistry.h | QObject 独立容器 | 又一套 | 有 |
| `PanelFactoryRegistry` | libs/registry/include/PanelFactoryRegistry.h | **static** 静态实例 | registerPanel/types | 无 |
| `UiSlotRegistry` | libs/registry/include/UiSlotRegistry.h | 实例自定义容器 | declareSlot/bindLocal | 无 |
| `ExtensionRegistry` | libs/registry/include/ExtensionRegistry.h | 实例七张贡献表 | mount/unmount | 有 |
| `BuiltinModuleRegistry` | host/include/BuiltinModuleRegistry.h | static | 自定义 | 无 |

### 1.2 诊断（整改依据）

`Registry<T>` 当初承诺"机制唯一"，实际只管住了**存储层**（key→条目有序容器）。
注册表机制的四层中，它只覆盖最底层：

1. **存储**（key→条目、保序）——已管住 ✅
2. **身份**（这张表是什么 kind、可枚举）——❌ 缺失
3. **生命周期**（增删通知世界——统一信号）——❌ 各家自己发明，方言不一
4. **可观测**（全系统有哪些表、各多少条、谁刚变化）——❌ 无法回答

**结论**：机制重心从模板挪到基类。`Registry<T>` 降级为存储实现细节（继续用，不删），
`RegistryBase` 承担身份/信号/可观测。参考 RT-Thread：注册是对象模型的一部分，
不是容器功能——子类自动获得注册能力，只实现自己的私有逻辑。

### 1.3 两种注册表的区分（决定谁继承基类）

- **系统注册表**（活的、有生命周期、要通知、要被枚举）→ 继承 `RegistryBase`：
  DatasetRegistry、SourceRegistry、DerivedSeriesRegistry、InteractionRegistry、
  UiSlotRegistry、ExtensionRegistry
- **纯查找表**（死数据、进程一份、无生命周期）→ **不继承**，维持现状：
  `Registry<T>`/`StaticRegistry` 直接使用方（滤波器目录等）、宏自注册机制

## 2. 目标设计

### 2.1 RegistryBase（新文件 libs/registry/include/RegistryBase.h）

```cpp
// 系统注册表的统一基类：身份 + 统一信号 + 可观测。参考 RT-Thread rt_object。
// 存储不在此处——子类自选容器（Registry<T> 模板或自定义），基类只管机制。
class RegistryBase : public QObject
{
    Q_OBJECT
public:
    // 类型标签（相当于 rt_object 的 type），如 "dataset"/"source"/"panel-factory"。
    virtual QString kind() const = 0;

    // 泛化查询（可观测层，全系统统一词汇；领域 API 不受影响）。
    virtual int count() const = 0;
    virtual QStringList keysAsStrings() const = 0;  // key 转 string（诊断/枚举用）

    // 【增补 1】Owner（提供者）一等公民：每条登记归属一个提供者（包/模块），
    // 按提供者原子撤销成为基类统一能力——消除 ExtensionRegistry 七张贡献表
    // mount/unmount 各三遍循环、UiSlotRegistry::unbindProvider 的复制粘贴。
    // 子类实现：记 key→owner 映射，撤销时按 owner 过滤。
    virtual bool removeByOwner(const QString &owner) = 0;

    // 【增补 2】变更序号 + 批量通知。
    //   revision()：单调递增，任何增删 +1——UI 缓存"比一个 int"即可判脏，
    //   不必连信号，解耦且防泄漏。
    //   beginBatch/endBatch：批量挂载（如 M3 装一个包 → 七张表×N 条目）期间
    //   抑制 objectAdded/objectRemoved 洪水；endBatch 发一次 changed(keys)。
    quint64 revision() const;
    void beginBatch();
    void endBatch();

    // 构造时自登记到 Hub（等价 rt_object 挂进 kernel object container）。
    // 【增补 3】Hub 由组合根（AppContext）创建并持有，构造时传入——
    // 禁止全局单例：① 测试间 hub 隔离，枚举断言互不可见；② 符合静态纪律
    // （"有生命周期的状态归组合根"）。static 注册表（R4）由 host 在装配时
    // 显式 attach 到组合根 hub。
    RegistryBase(RegistryHub &hub, const QString &name, QObject *parent = nullptr);
    ~RegistryBase() override;   // 析构自动从 Hub 摘除

    QString registryName() const;

Q_SIGNALS:
    // 统一信号【拍板：带 key】——消费方可精准响应"某条"，无需全量刷新。
    // key 用 QVariant 装载（DatasetId=int / 面板=QString 各表不同）。
    void objectAdded(QVariant key);
    void objectRemoved(QVariant key);
    // 批量收口：endBatch 时一次发出（keys 为本批次全部受影响条目）。
    void changed(QVariantList keys);
};
```

### 2.2 RegistryHub（新文件 libs/registry/include/RegistryHub.h）

```cpp
// 注册表全局枚举点（等价 RT-Thread kernel object container）。
// 【增补 3】实例由组合根（AppContext）创建并持有——不做静态单例，
// 测试中每个 App 独立 hub，枚举/断言完全隔离。
class RegistryHub
{
public:
    void attach(RegistryBase *reg);      // RegistryBase 构造时自动调
    void detach(RegistryBase *reg);      // RegistryBase 析构时自动调
    QList<RegistryBase *> registries() const;                  // 全部注册表
    RegistryBase *find(const QString &kind) const;             // 按 kind 查
};
```

### 2.3 诊断出口：`diag.registries` 意图

host 注册 view action，返回 QVariantList（每表一项）：

```
[ {kind:"dataset", name:"数据集", count:2, keys:["1","2"], revision:7},
  {kind:"panel-factory", count:9, keys:[...9 个面板类型], revision:9},
  ... ]
```

这是整改的核心验收物——整改后系统第一次能回答"我现在有哪些注册表、各有什么"。

### 2.4 设计拍板（已定，执行 agent 不再讨论）

1. **信号带 key**（`objectAdded(QVariant)`）——为画布联动（M2.6 遗留：
   派生序列自动叠加）铺路。各子类旧的具名信号（datasetAdded 等）改为
   inline 转发到基类信号 + 保留旧信号本体（旧名 emit 旧信号，旧信号同时
   也 emit 基类信号，或旧信号保留由调用点双 emit——以测试最小改动为准）。
2. **只统一元层，领域 API 不改名**——`DatasetRegistry::get/add/remove` 等
   领域词汇原样保留；基类只统一 `kind/count/keysAsStrings/objectAdded/
   objectRemoved/removeByOwner/revision/batch`。禁止为了统一而批量改调用点。
3. **【增补拍板】Hub 归组合根**——`RegistryHub` 实例由 AppContext 创建持有，
   不做静态单例（测试隔离 + 静态纪律）；static 注册表由 host 装配时显式 attach。
4. **【推迟】贡献校验钩子**（validate/贡献描述符/id 规则）——M2.8 里所有登记
   都是我们自己写的代码，校验是空转；M3 第三方包进场时再做（届时威胁才真实：
   重名/坏 id/缺字段）。基类设计时**预留**虚函数位即可，不实现。

## 5.5 想过但否决的（记录防重谈，执行 agent 不必评估）

| 候选 | 否决理由 |
|---|---|
| CRTP 替代虚函数（省虚调用） | 注册表操作是低频人机交互节奏，虚调用开销不存在；牺牲多态可观测性不值 |
| 侵入式链表（真 rt_object 式，对象自带 node） | 条目是值类型/句柄（Dataset 是门面、工厂是 function），侵入式要求条目稳定地址；**范式**（身份+全局枚举）已吸收，**实现**不照搬 |
| 完整 DI 容器 / Qt 插件系统 | 重量级错配：缺的是"枚举+通知"，不是依赖解析和动态加载 |
| 事件溯源（注册表变更持久化回放） | 会话级生命周期，重启即重建，持久化无意义 |
