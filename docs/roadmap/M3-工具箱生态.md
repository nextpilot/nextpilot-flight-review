# M3 · 工具箱生态（首批）

> 状态：规划中（阶段 3 启动前的地基：M2.x 特色底座完成度直接决定工具箱能做多少）。
> 定位：**业务知识变现的种子**——竞品学不走的壁垒在这里（方案文档第 8 节风险表）。

## 目标

非开发者（普通飞控工程师/CAN 测试工程师）能装包、用包、出报告；
外部开发者能按文档做出自己的包。

## 条目

| # | 执行条目 | 验收条目 |
|---|---|---|
| 3.1 | 工具箱打包格式 + 安装器（复用 Pack mount/unmount） | zip 包双击/拖入即装即卸；元数据校验失败给明确报错 |
| 3.2 | 首发工具箱之一：**PX4 调参包**（振动/EKF 分析面板 + 检查清单报告模板 + 示例数据 + 文档页） | 非开发者 10 分钟内装包并用它出一份调参报告 |
| 3.3 | 首发工具箱之二：**CAN 诊断包**（DBC 解析 + 报文浏览器强化 + 信号统计） | 拖入 DBC + blf 即出信号列表与曲线 |
| 3.4 | 工具箱开发文档（第三方如何做包） | 外部人按文档能做出一个 hello-world 包并装进 PlotScope |

## 方案纲要（阶段 3，方案文档第 5 节）

1. **打包格式**：工具箱 = extensions 领域包 + 清单（Pack 机制已有）→
   补 zip/目录归一格式与元数据（名称/版本/兼容性/作者）；
2. **安装与更新**：本地目录扫描起步（复用 mount/unmount），远端仓库与更新后续再说；
3. **文档门槛**：每个工具箱必须带示例数据 + DocEntry 文档页（机制已有），**无文档不合入**；
4. **首批选题储备**（除 3.2/3.3 外）：
   - GNSS 质量包：定位精度/卫星健康分析；
5. **授权**（若商业化）：离线 License 校验 + 工具箱加密分发——做在 Pack 装载层，不散落各处。

## 与 M2 的依赖关系

| 工具箱能力 | 依赖的 M2 底座 |
|---|---|
| 检查清单报告模板 | M2.3 报告导出（ReportTemplate 贡献）|
| 批量调参分析 | M2.4 批量处理 |
| 调参后编辑坏点/重算 | M2.5 数据编辑器 |
| Python 依赖的分析面板 | M2.6 Python 脚本引擎 |

→ 因此 M3 开工的前提是 M2.3/M2.4 落地；3.2 PX4 调参包是第一批验收的杀手场景。

## 杀手场景（验收演示）

普通飞控工程师：下载 PX4 调参包 zip → 拖进 PlotScope → 打开 ULog →
按检查清单跑振动/EKF 分析 → 一键出调参报告 PDF——全程不写一行代码。
