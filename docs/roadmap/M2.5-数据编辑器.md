## 评审要回答的核心问题（2.5.0）

1. **版本粒度**：每次编辑一个 vN？编辑会话合并？（Rust kernel 列存不可变块是天然底座，
   COW 换页成本低，但版本爆炸要有 merge/回收策略）
2. **派生联动**：派生表达式引用的源列被编辑 → 重算时机（立即/失活标记/事务提交时）
   与重算范围（仅受影响派生）。
3. **undo 边界**：undo 栈随数据集生命周期还是随面板？跨数据集操作的入栈语义。
4. **与 LOD/live 的交互**：live 源数据允许编辑吗（一期倾向：只读源可编辑，live 源禁止）。
5. **内存红线**：100 万行 × 编辑副本的峰值内存预算与验收线。

## 杀手场景（验收演示）

## 🗄️ 搁置记录（2026-11 用户决策：短期无收益、受众小）

重启时可直接采用下述已论证方案（2.5.0 评审草案）：

- **核心架构：delta-overlay，不动 Rust kernel**。kernel ABI 是 append-only（无 in-place
  edit/删行/clone），编辑作为稀疏 overlay（改值 map + 删行 mask）挂在 EditSession 上，
  读时合并；commit 时一次性重放物化 vN（~10ms）。对比方案：kernel 加 COW 编辑 ABI
  （牵动 ABI 版本，二期再说）/ 每步全量重建（undo 栈内存爆炸）均被否。
- **五问结论**：① 版本粒度=编辑会话提交制（overlay 实时可见，commit 才出 vN）；
  ② 派生联动=事务提交时选择性重算（datasetVersionChanged → 仅受影响派生）；
  ③ undo 栈随 EditSession 随数据集生命周期，反向 delta 存储，GUI/脚本同栈；
  ④ live 源禁止编辑，LOD 无影响（提交后重抽）；
  ⑤ 内存红线=1 万单元格编辑 × 10 步撤销 < 10MB（稀疏 delta ≈ 行数×8B×2）。
- **意图族**：`data.edit.set / deleteRows / commit / undo / redo` +
  `data.versions / data.checkout`（checkout 倾向"版本链只追加"，未定稿）。
- 待定：checkout 语义、overlay 阶段派生是否防抖预览重算。
